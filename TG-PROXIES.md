# Telegram-прокси в KZM

Telegram-прокси — необязательные независимые компоненты Keenetic Manager.
Они не являются стратегиями Zapret и не участвуют в цепочках `nfqws`.
Установка, обновление, запуск, остановка или удаление прокси не перезапускают
`nfqws`, firewall и сетевые интерфейсы Keenetic.

## Доступные реализации

| Компонент | Upstream | Режим | Порт | Статус |
| --- | --- | --- | ---: | --- |
| `socks5` | [d0mhate/-tg-ws-proxy-Manager-go](https://github.com/d0mhate/-tg-ws-proxy-Manager-go) | SOCKS5 | 1080 | экспериментально |
| `rust` | [p01ntov/tg-ws-proxy-rs-private](https://github.com/p01ntov/tg-ws-proxy-rs-private) | MTProto | 2443 | рекомендуется |
| `mtproto` | [spatiumstas/tg-ws-proxy-go](https://github.com/spatiumstas/tg-ws-proxy-go) | MTProto | 1443 | экспериментально |

Начиная с версии 0.8.0 поддерживается только Keenetic `aarch64`/`arm64`. Разные порты
позволяют установить все варианты одновременно, однако обычно достаточно
одного. Для новой установки рекомендуется сначала попробовать `rust`.

## Меню и команды

`kzm` открывает общее числовое меню. В разделе «Установка и удаление» один и
тот же пункт устанавливает отсутствующий компонент или удаляет уже
установленный. Раздел «Управление Telegram-прокси» содержит для каждого
компонента:

1. запуск и включение автозапуска;
2. остановку и отключение автозапуска;
3. ручную проверку и установку обновления;
4. показ ссылки подключения;
5. удаление.

Все действия выбираются цифрами. Enter возвращает в предыдущее меню. Прежнее
меню Zapret доступно первым пунктом или напрямую через `kzm zapret`.

Для автоматизации доступны команды:

```sh
kzm components status
kzm components install rust
kzm components update rust
kzm components start rust
kzm components stop rust
kzm components restart rust
kzm components link rust
kzm components remove rust --yes
```

Вместо `rust` допустимы `socks5` и `mtproto`. Фонового расписания и
автоматического обновления нет. Команда `update` проверяет upstream и изменяет
только явно выбранный уже установленный компонент; пункт общего меню
«Обновить установленные Telegram-прокси» делает то же по очереди для всех
установленных вариантов.

## Сеть и секреты

При первой установке KZM определяет приватный LAN IPv4 роутера и создаёт
конфиг, привязанный именно к нему. Адреса `0.0.0.0` и публичные адреса не
принимаются. Менеджер не создаёт правил firewall и не открывает доступ с WAN.

Конфиги находятся здесь:

```text
/opt/etc/kzapret-manager/components/socks5.conf
/opt/etc/kzapret-manager/components/rust.conf
/opt/etc/kzapret-manager/components/mtproto.conf
```

Они создаются с режимом `0600`. Для SOCKS5 локально генерируется пароль, для
MTProto — 32-символьный hex-секрет. Ссылки `tg://` не печатаются при запуске,
в общем состоянии или в безопасном журнале. Они раскрываются только пунктом
«Показать ссылку подключения» или командой `kzm components link ...`.

Все три процесса запускаются от непривилегированного пользователя `nobody`.
Rust получает секрет через переменную окружения. У двух Go-upstream нет
эквивалентного безопасного интерфейса: SOCKS5-логин/пароль и MTProto-секрет
передаются аргументами процесса; `root` может их прочитать. На обычном Keenetic
это не раскрывает их клиентам LAN, но доступ к root/SSH должен оставаться
доверенным.

Значения по умолчанию:

| Компонент | Bind | Порт | Дополнительное ограничение |
| --- | --- | ---: | --- |
| SOCKS5 | приватный LAN IPv4 | 1080 | логин `telegram` и случайный пароль |
| Rust MTProto | приватный LAN IPv4 | 2443 | гибридный маршрут, пул 2, максимум 32 соединения |
| Go MTProto | приватный LAN IPv4 | 1443 | без загрузки изменяемого списка Cloudflare |

Перед запуском проверяется, что TCP-порт свободен. PID сверяется с точным
путём бинарника компонента, поэтому повреждённый или подменённый PID-файл не
используется для остановки чужого процесса.

### Маршрут Rust v2 по умолчанию

KZM использует совместимый форк `p01ntov/tg-ws-proxy-rs-private`, основанный
на `valnesfjord/tg-ws-proxy-rs`. В нём сохранены флаги, переменные окружения и
протокол upstream, но исправлено двойное расходование таймаута и порядок
fallback-подключений. Поэтому существующий конфиг `rust.conf` обновляется без
смены секрета или ссылки подключения.

KZM запускает Rust в совместимом гибридном режиме. Проверенный Cloudflare shortlist
используется первым, потому что нестабильный direct WebSocket создаёт паузы между
медиапорциями. Новые соединения распределяются по рабочим доменам round-robin,
чтобы один Cloudflare endpoint не ограничивал весь медиапоток.
Прямые endpoint'ы `2:149.154.167.220` и `4:149.154.167.220` сохраняются как резерв,
а прямой TCP остаётся последним fallback. Ожидание резервного direct WebSocket
ограничено тремя секундами.

Shortlist хранится в сервисном профиле KZM и не зависит от доступности GitHub при
запуске. Если все Cloudflare-домены временно недоступны, binary переходит к direct
DC2/DC4 и затем к прямому TCP. Системные `HTTP_PROXY`, `HTTPS_PROXY` и SOCKS не
наследуются; запуск не перезапускает `nfqws`, firewall или интерфейсы Keenetic.

## Как устанавливаются файлы

KZM намеренно не использует upstream OpenWrt-инсталляторы, LuCI/UCI-скрипты и
feed-helper. Для каждого компонента он:

1. читает последний релиз из GitHub Releases API;
2. выбирает точный asset для `aarch64`;
3. требует опубликованный GitHub digest вида `sha256:...`;
4. скачивает asset во временный каталог и проверяет SHA-256;
5. ограничивает загрузку 32 MiB и держит временные файлы в `/tmp`, а не на
   флешке `/opt`;
6. проверяет ожидаемый формат asset и ELF64 AArch64;
7. атомарно устанавливает бинарник под уникальным именем.

Для пакета spatiumstas IPK используется только как контейнер. KZM проверяет
пути, `Package`, `Version`, `Architecture` и извлекает только ожидаемый бинарник.
Скрипты `postinst`,
готовый upstream init-скрипт и команды подключения opkg feed не выполняются.
Если digest уже установленного тега внезапно изменился, обновление блокируется
до появления нового тега.

## Ограничения безопасности

- `rust` — рекомендуемый вариант со включённой проверкой TLS. Процесс
  запускается от штатного непривилегированного `nobody`. Список community
  Cloudflare меняется upstream и может временно содержать недоступные домены;
  для постоянной максимальной надёжности нужен собственный Cloudflare-домен
  или Worker. Upstream сообщает о возможном росте памяти, поэтому
  KZM оставляет небольшой пул и лимит в 32 одновременных соединения. Это
  ограничение нагрузки, а не строгий лимит памяти процесса.
- `socks5` считается экспериментальным: его WSS-клиент отключает проверку
  TLS-сертификата, а опубликованный бинарник собран Go toolchain с известными
  уязвимостями, исправленными в более новых версиях Go.
  Доступ ограничивается доверенной LAN и случайным паролем, но это не заменяет
  обновление upstream.
- `mtproto` считается экспериментальным: upstream использует Go toolchain,
  снятый с поддержки, а его WSS-клиент отключает проверку TLS-сертификата.
  Отключение загрузки списка Cloudflare уменьшает поверхность риска, но не
  устраняет эту особенность бинарника.

Ни один из вариантов не следует публиковать в WAN без отдельной осознанной
настройки firewall. Перед выбором экспериментального варианта нужно оценить
описанные ограничения и проверить актуальное состояние его upstream.
