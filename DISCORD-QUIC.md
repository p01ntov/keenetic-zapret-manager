# Discord и QUIC на Keenetic

## Что включает менеджер

`kzm strategy set discord on` добавляет переносимый блок классического
`nfqws` для голосовых вызовов, STUN и UDP-медиа Discord:

```text
UDP 19294-19344,50000-50100
L7 discord,stun
fake stun.bin, repeats=6
```

Профиль `discord.media` выбирается отдельно:

```sh
kzm strategy list discord
kzm strategy set discord-media Dv1
```

Он обрабатывает TCP-порты `2053,2083,2087,2096,8443`. Доступные `Dv`
не вшиты в архив: `kzm update` извлекает их из актуального
`StressOzz/Zapret-Manager/Zapret-Manager.sh`, проверяет допустимые символы и
скачивает нужные fake-файлы. Выбор `off` отключает только TCP-блок
`discord.media`; голосовой UDP остаётся включённым.

SSH-меню Discord повторяет цифровые пункты Zapret Manager, но не маскирует
опасные несовпадения платформ. `50-discord-media` сохраняется как алиас уже
существующего блока KZM и включает его (второй блок и процесс не создаются).
Дополнительный пункт `9` явно включает или выключает базовый обход. Выбор fake для
`discord,stun` сохраняется отдельно; `off` удаляет только явные пути payload,
оставляя встроенные fake-данные `nfqws`:

```sh
kzm strategy set discord-script 50-discord-media
kzm strategy set discord-fake stun.bin
```

QUIC управляется независимо:

```sh
kzm strategy set quic on
```

Это добавляет `nfqws`-фильтр UDP/443 с fake QUIC для встроенного списка
YouTube. Он не предназначен для перехвата всего UDP-трафика роутера.

Если ролик по прямой ссылке открывается, а само приложение YouTube не грузится
или позже зависает, это похоже на разницу транспортов: браузер либо уже открытое
соединение может работать по TCP, тогда как приложение пробует HTTP/3 поверх
QUIC (`UDP/443`). Это полезный признак, но не доказательство: похожий результат
дают IPv6, VPN/мобильная сеть телефона, DNS и правила Mihomo. Основные домены
приложения (`youtubei.googleapis.com`, `youtubei-att.googleapis.com`,
`youtube.googleapis.com`,
`googlevideo.com`, `ytimg.com`, `ggpht.com`) уже входят во встроенный
`youtube.list`; добавлять широкий `googleapis.com` без диагностики не нужно.

## Почему не копируются OpenWrt-скрипты `50-*`

Пункты Zapret Manager `50-stun4all`, `50-quic4all` и
`50-discord-media` — не самостоятельные стратегии `nfqws`. Это хуки
bol-van `custom.d`, которые создают дополнительные процессы/очереди и
сигнатурные правила `nft` либо `iptables -m u32`. В их исходниках отдельно
указана зависимость NFT-варианта от более нового ядра; Keenetic-интеграция
имеет другую init-систему и не предоставляет функции `custom.d`.

Поэтому их дословная установка могла бы оставить лишние правила NFQUEUE или
оборвать трафик после перезапуска. Пункты `50-stun4all`, `50-quic4all` и
старый `50-discord` показывают понятный отказ и ничего не меняют: KZM не
подменяет их небезопасным захватом UDP 1-65535 и не подключает замороженный
ipset. Источники всё равно проверяются командой `kzm update`, а их URL и
статус совместимости записываются в `strategies/discord-scripts/sources.tsv`.

Пункт с 200 финскими `hosts` также информационный: native `ip host` Keenetic
ограничен 64 записями, а DNS обслуживает `ndnproxy`, не OpenWrt `dnsmasq`.
KZM не меняет `/etc/hosts`, DNS или службы этим пунктом.

## Безопасный порядок применения

```sh
kzm update
kzm strategy set discord on
kzm strategy set discord-media Dv1
kzm strategy set quic on       # только если UDP/443 не блокирует другой сервис
kzm preview
kzm apply                      # записывает конфиг, не перезапускает сеть
kzm service restart --yes      # выполнять отдельно при локальном доступе
```

`kzm update` также не применяет профили и не перезапускает службу.

## Проверка без глобального включения

Начиная с версии `0.5.0` доступен canary-режим. Он использует отдельный бинарник и
NFQUEUE, не останавливая текущий `nfqws2`/`nfqws`:

```sh
kzm test engine-update
kzm test suite current
kzm test voice start CLIENT_IP 120
kzm test youtube start PHONE_WIFI_IPV4 Yv08 120
kzm test status
kzm test stop
```

Для voice canary после запуска нужно создать новое соединение — выйти и
снова войти в голосовой канал. Тест использует fake, выбранный в пункте `8`,
но не записывает production-конфиг. Правило ограничено одним клиентом и
Discord-диапазонами UDP; watchdog снимает его автоматически. Аналогичная
команда `kzm test quic start PHONE_WIFI_IPV4 120` проверяет IPv4 UDP/443
одного телефона. Перед проверкой нужно отключить на телефоне мобильные данные
и VPN, принудительно закрыть приложение, снова открыть его и запустить новое
видео. Через 120 секунд watchdog удалит временную очередь и процесс; немедленный
откат — `kzm test stop`. Production-конфиг и основной `nfqws` не меняются.

Интерпретация результата:

- ненулевой `pkts` в `KZM_CANARY` означает, что IPv4 QUIC телефона дошёл до
  тестовой очереди; если в этот момент приложение заработало, QUIC-блок стоит
  рассматривать для постоянной конфигурации;
- нулевой `pkts` ничего не доказывает: приложение могло выбрать IPv6, другой IP,
  VPN/мобильную сеть, сохранить старое соединение либо попасть под перехват или
  `REJECT` Mihomo до `POSTROUTING`;
- ненулевой `pkts` при неработающем приложении означает, что одной текущей
  QUIC-стратегии недостаточно; это не повод включать её глобально вслепую.

IPv6-canary намеренно не создаётся. Для него потребовались бы отдельные
`ip6tables`/`nft`-правила, стабильный IPv6-адрес телефона и проверка IPv6
NFQUEUE на конкретной прошивке Keenetic. Это расширило бы затрагиваемый трафик
и сделало автооткат менее предсказуемым. Текущий тест остаётся узким и
IPv4-only; при активном IPv6 нулевой счётчик считается неопределённым
результатом. QUIC-canary не меняет правила Mihomo. Отдельный YouTube TCP
canary при подтверждённой цепочке `MIHOMO_REDIRECT` может временно добавить
точный bypass только для IPv4 телефона и TCP/443; тот же watchdog удаляет его
при остановке или по TTL, конфигурационные файлы Mihomo не меняются.
