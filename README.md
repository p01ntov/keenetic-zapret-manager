# Keenetic Zapret Manager

Локально написанный менеджер классического `zapret/nfqws` для Keenetic +
Entware. Он импортирует актуальные стратегии `v1-v10`, 21 основной профиль
Flowseal, `Yv` для YouTube, `Dv` для `discord.media`, Discord voice/STUN и
игровой UDP. Полный тест использует тот же базовый набор доменов, что
StressOzz/Zapret-Manager, и DPI-цели Hyperion (на момент проверки — 59
адресов). Свои домены, IPv4/IPv6-адреса и CIDR-подсети добавляются прямо из
SSH-меню. Менеджер не зависит от OpenWrt, UCI или LuCI.

Начиная с версии 0.8.0, `kzm` также управляет тремя необязательными
Telegram-прокси. Это отдельные процессы со своими бинарниками, конфигами,
PID-файлами и портами; они не подменяют Zapret и не меняют его правила.
Рекомендуемый вариант — MTProto-реализация Rust от valnesfjord. Два Go-варианта
оставлены как экспериментальные. Подробности и ограничения приведены в
[TG-PROXIES.md](TG-PROXIES.md).

Главное правило безопасности: выбор стратегии, запись конфига и перезапуск
службы — три разные операции. `kzm update`, `kzm strategy set` и обычный
`kzm apply` никогда не перезапускают сеть.

## Совместимость

Менеджер рассчитан на классический пакет `nfqws-keenetic` и его конфиг
`/opt/etc/nfqws/nfqws.conf`. Он не подставляет старые `--dpi-desync` стратегии
в `nfqws2-keenetic`, поскольку zapret2 использует другой Lua-формат.

Оба пакета конфликтуют на уровне opkg. Поэтому переход с уже установленного
`nfqws2-keenetic` выполняется отдельно и только после резервного копирования.
Сам `install.sh` движки не удаляет, службы не запускает и не перезапускает.
Пошаговый сценарий вынесен в [MIGRATION.md](MIGRATION.md).

Для HTTPS-обновлений менеджер предпочитает `curl`, затем использует `wget`.
На некоторых сборках Keenetic системный `wget` падает на HTTPS; в этом случае
достаточно безопасно установить загрузчик командой `opkg install curl`.

Установка Telegram-прокси в 0.8.0 поддерживается только на Keenetic с
архитектурой `aarch64`/`arm64`. Менеджер привязывает каждый прокси к
обнаруженному приватному LAN IPv4 и не открывает его порт на WAN.

## Установка менеджера

Скопировать архив на роутер, распаковать и выполнить:

```sh
sh install.sh
```

Затем, когда классический `nfqws-keenetic` уже установлен:

```sh
kzm update
kzm strategy list
kzm strategy set general v7
kzm strategy set youtube Yv08
kzm strategy set discord off
kzm strategy set discord-media Dv1
kzm strategy set quic off
kzm preview
kzm apply
```

Последняя команда только записывает конфиг. Осознанное применение с
перезапуском:

```sh
kzm service restart --yes
```

Или одной командой с автоматическим откатом конфига при ошибке запуска:

```sh
kzm apply --restart --yes
```

## SSH-меню

Команда `kzm` без аргументов открывает новое общее числовое меню Keenetic
Manager. В нём видны состояния Zapret и всех трёх Telegram-прокси, а пункты
ведут в настройку Zapret, установку/удаление и управление прокси. Вводить
технические имена компонентов не требуется.

Пункт «Zapret — стратегии, сайты и тесты» открывает прежнее меню Keenetic
Zapret Manager. Его же можно открыть напрямую командой `kzm zapret`: над
пунктами показаны выбранные стратегии, состояние Discord/YouTube, движок,
дата каталога и наличие неприменённых изменений.

Главные разделы подменю Zapret:

- **Меню стратегий** — сайты, YouTube, Discord, QUIC, игровой UDP и область
  действия;
- **Мои сайты и IP/подсети** — добавление доменов, IPv4/IPv6 и CIDR,
  просмотр и удаление записей по номеру;
- **Меню тестирования стратегий** — проверка текущего профиля по полному
  списку, долгий автоподбор `v + Flowseal`, подбор по своим доменам и
  двухминутные проверки Discord/QUIC для одного устройства;
- **Обновить стратегии и файлы обхода** — только скачивание каталога, без
  изменения активного конфига;
- **Применить выбранные настройки** — отдельное подтверждаемое действие с
  резервной копией и откатом;
- **Дополнительные возможности** — бэкапы, технический просмотр,
  диагностика и очистка журналов.

В подменю Enter возвращает назад, в главном меню — выходит. Технические имена
профилей (`v7`, `Yv08`, `Dv1`) показываются рядом с понятным состоянием, а
выбираются по номеру. По номеру также удаляются пользовательские записи и
выбираются резервные копии. Полный текст вводится только для новых данных —
домена, IP/CIDR или адреса тестового устройства. Если обнаружен
`nfqws2-keenetic`, пункт применения объяснит
несовместимость и завершится без записи файлов или перезапуска.

Общее меню содержит отдельный раздел «Установка и удаление» для
`nfqws-keenetic`, TG SOCKS5 от d0mhate, TG Rust от valnesfjord и TG MTProto от
spatiumstas. У каждого установленного прокси есть числовое меню запуска с
автозапуском, остановки с отключением автозапуска, ручной проверки обновления,
показа ссылки и удаления. Ссылка
подключения содержит пароль или MTProto-секрет, поэтому она выводится только
по явному выбору пользователя.

```text
kzm cleanup --yes           очистить auto.list и его лог
kzm storage status          размер безопасно очищаемых журналов
kzm storage cleanup --yes   очистить журналы Mihomo/KZM без restart
kzm test engine-update      извлечь отдельный nfqws только для тестов
kzm test suite current      текущая стратегия на полном списке
kzm test suite all          полный автоподбор v + Flowseal
kzm test suite v            только профили v
kzm test suite flowseal     только профили Flowseal
kzm test domain x.com ...   v + Flowseal на своих доменах
kzm test general            короткий старый тест v на Discord API
kzm test voice start IP     двухминутный ГС canary для одного устройства
kzm test quic start IP      двухминутный IPv4 QUIC canary для одного телефона
kzm test youtube start IP Yv08 120
                            TCP-профиль YouTube для одного телефона
kzm test status|stop        счётчики или немедленное снятие canary
kzm components status       состояние Zapret и Telegram-прокси
kzm components status rust  состояние выбранного Telegram-прокси
kzm components install rust [--yes]
kzm components update rust  проверить и установить обновление вручную
kzm components start rust
kzm components stop rust
kzm components restart rust
kzm components link rust    явно показать ссылку с секретом
kzm components remove rust --yes
```

Вместо `rust` в командах компонентов можно указать `socks5` или `mtproto`.
Фонового автообновления нет: установка обновления начинается только из меню
или командой `kzm components update ...`. Операции с Telegram-прокси не
перезапускают `nfqws`, firewall или сетевые интерфейсы Keenetic. Установка и
удаление самого `nfqws-keenetic` — отдельное явно подтверждаемое действие.

Режимы `scope`:

- `all` — обрабатывать весь подходящий трафик, кроме списка исключений;
- `list` — только домены из `kzm domain add ...` и адреса/подсети из
  `kzm network add ...`;
- `auto` — пользовательские цели плюс автоматическое обнаружение доменов.

Домены и сети собираются в два отдельных профиля одной выбранной стратегии.
Так они работают как «домен ИЛИ сеть», а не как пересечение двух фильтров.
Сети ограничивают обработку только на портах самой стратегии (обычно TCP/443
или TCP/80,443), а не означают перехват вообще всего трафика подсети. Файл
подсетей принимает IPv4, IPv6 и CIDR по одной записи в строке.

Работающий классический `nfqws` автоматически перечитывает подключённые
hostlist/ipset после их изменения. Пока на роутере активен `nfqws2`, KZM лишь
сохраняет пользовательские цели и явно показывает, что они ещё не участвуют
в трафике.

Обновление каталога никогда не меняет уже записанный `nfqws.conf`. Новая
версия выбранной стратегии попадёт в работу только после явных `kzm apply` и
`kzm service restart --yes`.

## Telegram-прокси

Компоненты устанавливаются независимо и могут сосуществовать на разных
TCP-портах:

- `socks5` — TG WS Proxy SOCKS5 by d0mhate, порт `1080`, экспериментально;
- `rust` — TG WS Proxy Rust by valnesfjord, порт `2443`, рекомендуется;
- `mtproto` — TG WS Proxy MTProto by spatiumstas, порт `1443`,
  экспериментально.

Rust по умолчанию использует совместимый гибридный маршрут: DC4 идёт сначала
напрямую через WebSocket, остальные Telegram DC — через загружаемый при запуске
community-список Cloudflare. Список хранится только в памяти, а системные
outbound-прокси и случайная балансировка CF-доменов отключены.

Конфиги находятся в `/opt/etc/kzapret-manager/components/`, создаются с
правами `0600` и содержат сгенерированные локально учётные данные. Бинарники,
службы, PID-файлы и журналы имеют разные имена, поэтому управление одним
прокси не останавливает остальные.

KZM не запускает upstream OpenWrt-инсталляторы и не подключает сторонние opkg
feeds. Он запрашивает метаданные последнего релиза через GitHub API, выбирает
точный asset для `aarch64`, проверяет опубликованный SHA-256 digest и только
затем устанавливает бинарник. Entware IPK от spatiumstas безопасно
распаковывается во временный каталог в RAM: проверяются метаданные пакета,
архитектура и ELF AArch64, а его `postinst`, init-скрипт и feed-helper не
исполняются. Размер загрузки ограничен 32 MiB, поэтому asset не должен засорять
флешку Entware. Подробная модель установки и замечания по безопасности — в
[TG-PROXIES.md](TG-PROXIES.md).

## Discord и QUIC

В SSH-меню Discord состоит из двух блоков:

- voice/STUN и UDP-медиа на диапазонах `19294-19344` и `50000-50100`;
- TCP-доступ к `discord.media` на портах `2053,2083,2087,2096,8443` с
  выбираемым профилем `Dv`.

Меню также повторяет пункты `1–8` из Zapret Manager и добавляет пункт `9`
для явного включения или выключения базового Discord-блока. Fake выбирается
только цифрой: `1–9` соответствуют оригинальному списку, `0` возвращает
встроенный payload `nfqws`. Выбор `50-discord-media` включает нативный
voice/media-блок KZM, но не запускает второй процесс и не дублирует очередь.

Команда `kzm update` каждый раз заново читает доступные `Dv` прямо из
`Zapret-Manager.sh`. На момент локальной проверки импортировались `Dv1-Dv17`.
QUIC вынесен в отдельный переключатель: он обрабатывает UDP/443 только для
встроенного списка YouTube и не включается вместе с Discord автоматически.

OpenWrt-хуки `50-stun4all`, `50-quic4all`, `50-discord-media` и старый
`50-discord` напрямую не устанавливаются. Они завязаны на `custom.d`,
функции init-системы bol-van и специальные правила `nft`/`iptables u32`,
которых нет в `nfqws-keenetic`. Менеджер использует переносимые фильтры
самого `nfqws` и штатные правила портов Keenetic. Подробное соответствие и
ограничения описаны в [DISCORD-QUIC.md](DISCORD-QUIC.md).

Если Mihomo или другой прокси уже блокирует UDP/443 правилом `REJECT`, перед
включением QUIC в `kzm` это правило нужно отключить отдельно. Сам менеджер
чужие конфиги не редактирует.

## Безопасная проверка до применения

Canary-тесты не вызывают `apply`, не меняют активный конфиг и не
перезапускают службы. Сначала один раз подготовить тестовый движок:

```sh
kzm test engine-update
```

Команда скачивает индекс официального `nfqws-keenetic`, проверяет SHA-256
пакета и извлекает только бинарник в каталог менеджера. `opkg install` не
выполняется, демон не запускается постоянно.

Проверка текущей стратегии по каталогу Zapret Manager/Hyperion:

```sh
kzm test suite current
```

Полный автоподбор:

```sh
kzm test suite all
```

Сейчас каталог состоит из 23 адресов, перечисленных в `prepare_urls` проекта
Zapret Manager, и 36 DPI-целей из `suite.v2.json` Hyperion — всего 59. При
`kzm update` список обновляется атомарно: повреждённая или слишком короткая
загрузка не заменяет предыдущий рабочий файл. Текущее число целей всегда
показывается в SSH-меню.

Тест сначала делает контроль без desync, затем запускает выбранные профили.
Для каждого профиля создаётся отдельная временная очередь `301`, а до восьми
HTTPS-запросов выполняются параллельно. Во время проверки выводится только
текущий профиль и его номер, без повторения десятков строк по каждой цели:

```text
Тестируем стратегию: general (ALT7) (12/31)
```

Подробные результаты каждого HTTPS-запроса сохраняются в
`/opt/etc/kzapret-manager/results/last-strategy-test.csv`. Финальная сводка
показывает по одной строке на стратегию и сортируется по числу доступных целей
от меньшего результата к большему.

При этом основной Zapret не выключается, конфиг не переписывается и службы не
перезапускаются. Правило совпадает только с исходящим TCP/443 самого роутера,
помечает тестовые пакеты до рабочей очереди и имеет `--queue-bypass` и
watchdog. Перенаправленный трафик устройств не входит в это правило. Один
профиль может тестироваться не дольше примерно двух минут; полный набор из 31
профиля при большом числе таймаутов может занять 20–30 минут.

Результаты показывают общий счёт, сколько адресов стратегия открыла
относительно контроля (`+`) и сколько доступных в контроле сломала (`-`). Это
важно: одиночный `FAIL` может означать мёртвый сервер, а не блокировку DPI.
Рекомендация выдаётся только для профиля, который что-то открыл, не создал
регрессий и действительно провёл пакеты через очередь. Согласие пользователя
меняет лишь выбранный профиль KZM — конфиг и служба применяются отдельно.

Для точечной проверки можно передать до 25 доменов:

```sh
kzm test domain x.com discord.com
```

У каждого запуска уникальный ID, поэтому устаревший watchdog не может снять
правила следующей попытки. `kzm test stop` немедленно удаляет временный
процесс и правила.

ГС и QUIC требуют настоящего приложения на тестовом устройстве:

```sh
kzm test voice start 192.168.1.108 120
# выйти и заново войти в голосовой канал
kzm test status
kzm test stop

kzm test quic start 192.168.1.108 120
# отключить мобильную сеть/VPN, перезапустить приложение и открыть новое видео
kzm test status
kzm test stop

kzm test youtube start 192.168.1.108 Yv08 120
# тот же перезапуск приложения; профиль выбирается в меню по номеру
kzm test status
kzm test stop
```

Live-canary затрагивает только указанный IPv4 клиента и нужные TCP/UDP-порты.
Старое соединение в FastNAT не попадёт в тест — для ГС нужно переподключиться.
Voice-canary использует fake, выбранный в Discord-меню, поэтому варианты
можно сравнивать без записи production-конфига и без перезапуска основного
`nfqws`.
Через TTL правило и тестовый процесс удаляются автоматически; `test stop`
делает это немедленно.

Для YouTube нужно вводить именно IPv4 телефона из свойств Wi-Fi, а не адрес
компьютера с SSH. Меню поэтому не подставляет SSH-адрес в этот пункт. Если
прямая ссылка работает, но приложение не грузится или позже зависает, возможна
разница между TCP и HTTP/3/QUIC. Ненулевой `pkts` в `KZM_CANARY` подтверждает,
что IPv4 UDP/443 дошёл до теста; нулевой счётчик не является отрицательным
результатом при IPv6, VPN/мобильной сети или перехвате UDP/443 в Mihomo.

Если для TCP-теста обнаружена реальная transparent-цепочка
`MIHOMO_REDIRECT`, canary временно ставит в неё точный `RETURN` только для
IPv4 телефона и TCP/443. Это позволяет пакету дойти до тестового nfqws;
watchdog и `kzm test stop` удаляют именно это правило. Для QUIC/UDP такой
bypass не создаётся.

IPv6-canary менеджер намеренно не добавляет: стабильный адрес телефона,
IPv6 NFQUEUE и правила `ip6tables`/`nft` зависят от конкретной прошивки, а
параллельный перехват расширил бы риск теста. KZM только предупреждает об
активном IPv6 и не меняет IPv6 либо конфигурационные файлы Mihomo.

## Журналы Mihomo и MetaCubeXD

Web-панель MetaCubeXD хранит свой браузерный кэш на устройстве, с которого
она открыта, а не на флешке Keenetic. На роутере обычно растёт журнал процесса
Mihomo. Проверить и очистить только безопасные журналы можно из раздела
«Дополнительные возможности» либо командами:

```sh
kzm storage status
kzm storage cleanup --yes
```

Очистка обнуляет текущие `mihomo.log`/`kzapret-auto.log` и удаляет только их
ротации `.1`. Она не останавливает службы и не удаляет `cache.db`, конфиги,
подписки, rule-provider или файлы MetaCubeXD.

## Локальная проверка

Тесты рассчитаны на POSIX `sh`/BusyBox `ash`:

```sh
sh tests/run.sh
```

Тестовый root создаётся только под `/tmp/kzm-test-root`; реальный роутер в
тестах не используется.

Необязательная проверка против текущих upstream-репозиториев также работает
только в локальном контейнере/машине:

```sh
sh tests/integration-live.sh
```
